# Supabase: аккаунты и общий каталог

Этот каталог готовит серверную часть для «Якоря». Облачный проект не создан и не подключён: миграция и проверки выполнены локально. Пароли обрабатывает Supabase Auth; приложение не сохраняет и не читает пароли или их хеши. Прогресс чтения и импортированные личные книги остаются в локальном хранилище браузера.

## Подключение проекта

1. Создайте проект Supabase или выберите отдельный проект для этого сайта. Миграция рассчитана на новые таблицы с указанными именами; не применяйте её поверх чужой схемы `profiles` или `catalogue_books` без проверки совместимости.
2. В SQL Editor под владельцем базы выполните содержимое [`migrations/001_accounts_catalogue.sql`](migrations/001_accounts_catalogue.sql). Либо выполните `psql --set=ON_ERROR_STOP=1 --file=backend/migrations/001_accounts_catalogue.sql` с настроенным подключением владельца. Повторное применение этой же миграции сохраняет строки и административные назначения.
3. В настройках Data API оставьте `public` среди exposed schemas. **Не добавляйте `private` в exposed schemas.** Проверки RLS и явные grants уже входят в миграцию.
4. В Authentication включите вход по email и паролю, регистрацию новых пользователей и **Confirm email**. Автоматическое подтверждение email должно быть выключено перед назначением администратора: поле `email_confirmed_at` иначе не доказывает переход по письму. Для публичного использования настройте свой SMTP, адрес отправителя и ограничения отправки писем.
5. В Authentication → URL Configuration задайте Site URL с полным путём опубликованного GitHub Pages сайта и завершающим `/`, например `https://OWNER.github.io/REPOSITORY/`. Добавьте этот адрес в разрешённые Redirect URLs. Локальный адрес разработки добавляйте отдельно, если он нужен. Проверьте переход из письма подтверждения и восстановления пароля обратно в приложение.
6. В конфигурацию фронтенда внесите **Project URL** и **publishable key** (`sb_publishable_…`) либо legacy `anon` key. Эти значения допустимы в статическом сайте, потому что доступ ограничен RLS. Secret key, `service_role` key, строка подключения и пароль базы никогда не должны попадать в GitHub Pages, JavaScript, браузерное хранилище или коммит.

В настройках безопасности пароля установите минимум **10 символов**, чтобы серверная политика совпадала с формой сайта. Site URL для этой публикации: `https://peretyaginmstu-jpg.github.io/anchor-reader/`; тот же точный адрес добавьте в Redirect URLs. PKCE-ссылки подтверждения и восстановления открывайте в том браузере, из которого они были запрошены.

Перед включением облачной полки перенесите в неё исходные 16 произведений. Из корня проекта:

```sh
npm ci --ignore-scripts
cp .env.example .env
# Заполните SUPABASE_URL и SUPABASE_SECRET_KEY в локальном .env.
node --env-file=.env scripts/seed-catalogue.mjs
node scripts/configure-accounts.mjs https://PROJECT.supabase.co sb_publishable_PUBLIC_KEY
```

`.env` исключён из Git. Seed использует серверный секрет только в локальном процессе; он не записывает его в исходники и не перезаписывает существующие записи. После успешного наполнения секрет можно удалить из локального файла. Закоммитьте только публичный конфиг и опубликуйте сайт. При включённом облачном каталоге он становится общей полкой; публикация и скрытие в админке управляют именно им. Уже скачанные локальные копии сохраняются у читателей.

После подключения проверьте в отдельном окне: регистрацию, подтверждение email, вход/выход, восстановление пароля, доступ к своему профилю. Локальные SQL-тесты не проверяют Supabase Auth, доставку писем, настройки Redirect URLs или REST API облачного проекта.

## Первое назначение администратора

Администратор **не назначается первому зарегистрированному пользователю**. Поля `role`, `is_admin` и другие значения, которые клиент передаёт в user metadata, не влияют на права.

1. Зарегистрируйте нужный аккаунт обычным способом и подтвердите его email.
2. Подключитесь к PostgreSQL **как владелец базы**. Храните реквизиты подключения вне репозитория, например в локальном `PGSERVICE`/`.pgpass`, с доступом только владельцу файла.
3. Из корня репозитория выполните:

   ```sh
   psql --set=ON_ERROR_STOP=1 --set=admin_email='CONFIRMED_ACCOUNT_EMAIL' --file=backend/scripts/grant-admin.sql
   ```

   Замените заглушку в своём терминале; настоящий адрес не нужно записывать в исходники. Скрипт использует quoted SQL literal, требует ровно один существующий аккаунт и заполненный `email_confirmed_at`. Повторный запуск не создаёт дубликат. CLI-параметр может оставаться в истории вашего терминала — при необходимости передайте переменную из доверенного локального скрипта.
4. Обновите приложение после назначения. `rpc('is_admin')` начнёт возвращать `true` без добавления роли в JWT.

Пользовательский интерфейс администратора управляет каталогом и показывает список пользователей. Он не назначает администраторов. Даже `service_role` не имеет прямых прав на `private.admin_members`; операция назначения в этой реализации оставлена владельцу БД.

Отозвать доступ можно под владельцем базы, удалив соответствующий UUID из `private.admin_members`. Это вступает в силу при следующем запросе, без ожидания обновления JWT. Удаление пользователя из Supabase Auth также удалит его профиль и членство. Не изменяйте пароли SQL-командами.

## Контракт клиентского API

Все имена ниже — в схеме `public`. RPC-обёртки выполняются с правами вызывающего; привилегированные реализации находятся в `private`, имеют `search_path = ''` и проверяют `auth.uid()` по таблице членства.

| Объект | Поля / результат | Доступ из браузера |
| --- | --- | --- |
| `profiles` | `id uuid`, `display_name text`, `created_at timestamptz` | Пользователь читает только свою строку и обновляет только `display_name`. Создание — триггер Auth. |
| `catalogue_books` | `id text`, `title text`, `author text`, `year integer|null`, `source_url text|null`, `chapters jsonb`, `total_words integer`, `published boolean`, `created_at`, `updated_at` | Гость и читатель видят только `published=true`. Администратор видит все строки и может добавлять, менять, публиковать и удалять книги. |
| `rpc('is_admin')` | `boolean` | Только вошедший пользователь; `false` для обычного читателя или отсутствующего `auth.uid()`. |
| `rpc('admin_list_users')` | Массив `{id,email,display_name,created_at,last_sign_in_at,email_confirmed_at,is_admin}` | Только администратор с подтверждённым email. Для другого пользователя ошибка SQLSTATE `42501`. Пароли и хеши не возвращаются. |

Чтение каталога лучше разделить на список метаданных и загрузку текста выбранной книги, чтобы не скачивать все `chapters` сразу:

```js
const summaryFields = 'id,title,author,year,source_url,total_words,published,created_at,updated_at';
const list = await supabase.from('catalogue_books').select(summaryFields).order('title');
const book = await supabase.from('catalogue_books').select('*').eq('id', bookId).single();
const profile = await supabase.from('profiles').select('*').eq('id', user.id).single();
const saved = await supabase.from('profiles').update({ display_name: newName }).eq('id', user.id).select().single();
const role = await supabase.rpc('is_admin');
const users = await supabase.rpc('admin_list_users').range(0, 99);
```

Для длинных списков используйте постраничное чтение: настройки Data API могут ограничивать число возвращаемых строк. Проверяйте `error` каждого вызова. При изменении или удалении строки используйте возвращаемые данные, чтобы отличить успешное действие от нуля строк из-за RLS.

Администратор передаёт в insert/upsert только редактируемые поля книги. `created_at` и `updated_at` выставляются сервером. Новая книга по умолчанию имеет `published=false`.

```js
const result = await supabase.from('catalogue_books').upsert({
  id: 'example-book',
  title: 'Название',
  author: 'Автор',
  year: null,
  source_url: null,
  chapters: [{ title: 'Глава 1', paragraphs: ['Текст первого абзаца.'] }],
  total_words: 3,
  published: false,
}).select().single();
```

Ограничения данных:

| Поле | Ограничение |
| --- | --- |
| `display_name` | До 80 символов; пустое имя разрешено. При регистрации строка из metadata обрезается до 80 символов; неверный тип превращается в пустую строку. |
| `id` книги | 1–80 символов, `^[a-z0-9][a-z0-9_-]{0,79}$`. |
| `title`, `author` | Непустое название до 240 символов; автор до 160 символов, может быть пустым. |
| `year`, `source_url` | Год от −3000 до 3000 либо `null`; URL только `https://`, до 2048 символов, либо `null`. |
| `chapters` | 1–2000 объектов, только `{title, paragraphs}`; заголовок 1–300 символов; 1–20000 абзацев на главу, до 100000 на книгу. |
| Абзац | Непустая строка, не только пробельные символы, до 200000 символов. HTML не выполняется; клиент должен выводить строки как текст. |
| Размер текста | `octet_length(chapters::text)` до 20 MiB. |
| `total_words` | 1–2000000. Это ограниченная метаинформация клиента; SQL не дублирует правила RSVP-токенизатора. Клиент вычисляет значение через тот же токенизатор, что использует чтение. |

Личная позиция, скорость и прогресс пользователя не являются полями каталога и не публикуются вместе с книгой.

## Проверки PostgreSQL

Нужны Node.js 22+ и установленный PostgreSQL (`initdb`, `pg_ctl`, `psql`). Запуск из корня репозитория:

```sh
node backend/tests/run-postgres.mjs
```

Если исполняемые файлы отсутствуют в `PATH`, укажите каталог через `ANCHOR_PG_BIN`:

```sh
ANCHOR_PG_BIN=/path/to/postgresql/bin node backend/tests/run-postgres.mjs
```

Runner создаёт отдельный временный кластер PostgreSQL в `/tmp`, слушающий только локальный Unix socket, дважды применяет миграцию, запускает проверки и удаляет кластер. Он не использует облачный URL, проектную базу или Docker. Некоторые песочницы запрещают shared memory PostgreSQL; в таком окружении запуску нужны разрешения на локальный процесс БД.

Проверены **69 сценариев RLS/валидации + 8 сценариев bootstrap** на PostgreSQL 17: собственные/чужие профили, колонковые права, гости и читатели, опубликованные книги и черновики, административный CRUD/upsert, защищённый список пользователей, отозванные роли, каскадное удаление, ограничения текста, подтверждённый email и SQL-экранирование bootstrap-параметра.

[`tests/auth-fixture.sql`](tests/auth-fixture.sql) намеренно создаёт **тестовую минимальную** `auth.users` и функцию `auth.uid()`. JWT-идентичность задаётся тестом через `SET LOCAL`; в браузере её устанавливает проверяющий токен Supabase. Фикстура не реализует native Auth policies, выдачу JWT, хеширование паролей, HTTP/PostgREST или почтовые потоки. Эти слои требуют отдельной проверки после подключения настоящего Supabase.

## Основания схемы

Реализация следует рекомендациям Supabase по совместному применению [RLS и явных grants](https://supabase.com/docs/guides/database/postgres/row-level-security), [ограничению EXECUTE и `search_path` функций](https://supabase.com/docs/guides/database/functions) и [профилям, связанным с `auth.users`](https://supabase.com/docs/guides/auth/managing-user-data). Пользовательские metadata [редактируются самим пользователем и не подходят для авторизации](https://supabase.com/docs/guides/auth/users).
